# mvmAI

Pin a conversation to keep it first and prevent automatic archiving. Use right-click or long press for Pin, Unpin, Rename and Archive; on a phone, swipe left to reveal the action buttons. Unpin a chat before archiving it. Sending a new message moves its conversation to the top of the unpinned list. Opening an old conversation or receiving an answer does not change that order. Projects follow recent use, while automatic archiving follows the last sent message rather than merely viewing a conversation.

Administrators can click the provider and model above the composer to choose them for a new chat or change them in an existing conversation. A model change keeps the conversation history and adds a visible note; saved answers show their provider. A running reply must finish or be stopped before switching its model. Switching to another chat leaves its work running, and Send now on a queued message interrupts the current reply to send that message next. Usage bars show supported CLI subscription limits and reset countdowns as rounded squares progressing from green through yellow and orange to red, with readable labels and backgrounds that follow the theme. Tap the bar on a phone to cycle through available limits. A failed or slow refresh never empties the bars: the last good reading stays until a new one replaces it. A compact activity graph and elapsed timer appear while waiting for an answer; the graph rises when new CLI output arrives, with any burst lifting it well up and larger ones to the top so every CLI reads clearly, and settles to a faint pulse when no new output arrives. The same graph appears behind a working chat in the sidebar, without an extra status row or timer. Graph height reflects incoming activity, not reasoning complexity; API providers without activity events keep a flat line. New answers retain their response duration next to the date and time, including after reopening the chat.

With no project selected, the sidebar shows every conversation from every project, newest first, and each one says which project it belongs to or that it has none. The Projects list starts with No project, which shows only the conversations without a project; choosing a project shows only its own, as before, and choosing the same entry again returns to the full list. A new conversation started from the full list or from No project has no project; started inside a project it belongs to that project. The archive follows the same choice: its count and list cover everything on the full list, only the project's own inside a project, and only the conversations without a project under No project, and Delete all archived removes only what is listed. Under the conversations a single row shows the current branch on the left, with icons on the right to expand the project's files and the archive.

When the assistant offers a picture (PNG, JPEG, WebP or GIF) as a file, the chat shows it as a preview above the download button, and clicking it opens it larger. Opening a saved conversation scrolls to the newest messages after the view finishes loading.

Projects accept typed instructions and an optional instructions file when created or edited. Relative file paths resolve against the project folder, and the file is reread before every message. The current branch remains visible when View files is collapsed. Expanding View files displays the file tree once it is ready, without an intermediate loading layout, and reuses an already loaded tree. The Files gallery shows the current project’s files first and keeps other files in an expandable group.

Administrator downloads are copies in the profile’s dedicated chat-files folder. Deleting an archived conversation removes its attached files and download copies, retaining files still referenced by another chat and leaving project originals untouched. The deletion confirmation explains this cleanup. The desktop Premium terminal opens an interactive shell in the current project folder, or the signed-in Linux user’s home folder outside a project.

## Conversation compaction

When mvmAI summarizes older messages, chats with a saved Claude or Codex session also request native context compaction in that same session. The chat keeps its provider session ID. Claude must report a compaction boundary and a successful result; Codex must report a completed context-compaction item and successful turn. Only then does the interface replace older messages with its summary. A failed operation retains the visible history and reports that compaction failed. Maintenance and regular messages for the same chat run in sequence, and an outdated maintenance request is rejected before making AI calls.

This maintenance uses the chat’s pinned provider and model and consumes provider usage, including the summary request. Gemini continues to use its existing automatic context management; this integration does not add manual Gemini compression. Providers without an mvmAI-managed persistent CLI session receive the summarized conversation on subsequent requests.

## Resting chats and session restart

A chat with a saved CLI session (Claude, Codex, Gemini and others) continues that same session while you keep writing, because the provider keeps the conversation cached for a limited time after each answer. When the time since the chat's last answer is longer than the restart time, continuing the old session would make the provider read everything again at full price. In that case mvmAI starts a new session instead and sends it the latest summary, the messages after it and the new message, with both your questions and the assistant's answers. Work the old session did only internally, such as files it read, is not carried over. Chats saved before this behaviour have no recorded answer time and keep continuing their session until their next answer. The default is 60 minutes for every provider. With Premium the administrator can change it under **History** in the mvmAI settings, from 1 to 1440 minutes, for both the desktop and the public page; without Premium it stays at 60.

## Desktop terminal

mvmAI’s Premium terminal is an interactive shell beside the desktop chat. It starts in the active project folder, or the signed-in Linux user’s home folder outside a project, and works with any AI provider. It can float over the chat, dock on the right or bottom, or stay pinned to a conversation. With `tmux` installed, hiding or reconnecting keeps the shell running; closing the terminal ends its shell session. The terminal is available only on the desktop.

## Live progress, code and Git diffs

CLI chats display supported public messages and tool activity directly in the conversation while a task runs, without a separate scrollable progress box. Received events appear one at a time with about 350 ms between them and a brief entrance animation; reduced-motion preferences disable the animation. New events scroll the conversation to the latest activity. Commands start collapsed as a single-line preview with a status label. Expanding a command reveals its highlighted code and output; a status update preserves a manually expanded command. When the turn finishes, progress collapses into **Live progress**, which can be reopened in the current view. Final answers are never delayed by the display queue: any remaining events are retained inside the collapsed archive. Progress previews are transient and do not enter model history; reopening a saved conversation retains the final answer rather than the live event panel. Private reasoning and CLI session metadata are excluded. The server retains at most 100 public activity events per turn and polling requests only events after the client's cursor. Provider support varies: Codex agent messages and tool events and Claude streamed public text, tool inputs and matching tool results are recognized; this does not add streaming to API providers.

Fenced code blocks in messages have local syntax coloring for supported programming languages. Unknown languages remain plain code. Code and diff content is escaped before display. These previews do not send additional AI requests or add AI tokens.

In an administrator's Git project, **Git changes** lists Git-changed files whose modification time is at or after the message's start time. This only filters the file list: green `+` and red `−` counters and the read-only diff continue to include all current changes in each selected file compared with HEAD, including earlier uncommitted work. Existing untracked files are selected by the same timestamp rule. Deleted paths have no file modification time and are omitted from the time-filtered list. Concurrent manual edits or work from another chat may also appear. Filtering uses local filesystem timestamps, without file snapshots, additional AI requests or additions to model history.

The list is absent outside Git repositories. Binary files and untracked files above 2 MB have no line counters. File previews are capped at 512 KB. The diff endpoint requires an authenticated administrator and confines paths to the selected project, including resolving symlinks. External diff commands and text conversions are disabled. The branch indicator continues to reflect the repository's branch independently of the filtered file list.

Run the isolated Python checks with `venv/bin/python -m unittest discover -s apps/mvmai/tests -v`. They cover event filtering, bounded storage, polling ownership, final event delivery, Git additions/deletions, new files, unborn repositories and path confinement. No live chat data is used. Timestamp-filter tests verify that older files are hidden while selected files retain their full counters and diff. Compaction checks also cover provider completion signals, session ownership, outdated requests, failure handling and per-chat serialization. Run `node apps/mvmai/tests/test_compaction_client.cjs` to check that the interface waits for confirmation and retains history on failure.

The isolated browser checks run with `node apps/mvmai/tests/test_live_browser.cjs` when Playwright and its Chromium browser are available. `MVMAI_PLAYWRIGHT_MODULE` and `MVMAI_CHROMIUM` can point to an external installation. They verify desktop and mobile pacing, inline scrolling, final collapse, queued event retention, compact command expansion, Git counters and diff navigation.

## Previous mvmAgent tasks (Premium)

In mvmAI settings, enable **mvmAgent** in the Premium section. The agent mode opens project workspaces. The earlier standalone task board is no longer shown in the interface; its records stay in the database and its endpoints remain, and the description below documents how it worked. The switch between **Chats** and **mvmAgent** appears only to an authenticated Apps Hub administrator after the setting is enabled. A free desktop installation shows the locked agent control and opens the Premium dialog; the public page does not advertise unavailable Premium features. A downloaded Premium module and the setting are required server-side for every agent endpoint and browser asset. Disabling the feature, losing Premium or losing administrator access stops active work. The default is off.

Create a task with a title, goal, existing project and provider/model. Choosing an existing chat copies its project and pinned model into a separate agent conversation; it does not copy, modify or continue that chat's messages. Agent conversations do not appear in the ordinary chat list and cannot be opened or modified through its conversation endpoints. Switching modes preserves the mounted normal chat, its draft and any work already running there.

Press **Continue** to start background work. The model can create and update TODO steps and site rows with a title, action, status, draft, account, result, evidence URL and next action. Waiting entries require a next action; completed entries require a result, and completed site entries also require an evidence URL. These are agent-reported records, not independent proof of a site's response; the agent is instructed to verify a publication before marking it complete. The attention panel gathers waiting entries. The journal records model messages, research, board updates, approvals and execution results. Add manual corrections or instructions and use **Send and continue** when the task needs input. Board entries can be edited while work is paused.

The initial search implementation uses a public Bing RSS search feed and filters obviously unrelated results. Coverage is limited, especially for new or niche products, and search results must be read and checked. An optional **Brave Search API key** in mvmAI settings selects Brave's search service instead; its billing is separate from mvmAI. Public-page reads are restricted to HTTP(S) on public addresses, pin validated DNS results, do not follow redirects automatically and never use authenticated browser cookies.

Server execution must also be enabled through the existing administrator execution control on the surface being used. Agent commands always enter their own review queue, even when ordinary chat execution is automatic. Review the exact command, destination, account and draft content where supplied. **Approve** authorizes the displayed action; **Continue** executes approved actions. **Reject** returns a cancellation result to the model. Editing the table's draft does not change an already queued command: reject the command and ask the agent to prepare a replacement when its content needs to change. No command is executed by approving or editing a board row alone. Do not put passwords or API keys into draft content or shell arguments; use the site's existing credential mechanism.

This version does not provide a universal browser login, account vault or automatic registration flow. Site-specific publishing or browser automation can be requested through reviewed commands using available server tooling. CAPTCHA, two-factor authentication and other manual steps are represented as waiting items; the administrator completes them and reports the result. Tool availability and the chosen model's ability to use tools determine which tasks can be completed.

Each run allows 1–30 model rounds, default 12; reaching the limit pauses the task for review and manual continuation. Existing per-message credit pricing applies separately to each model request. At most two agent tasks run concurrently. A model request has a four-minute timeout, a shell command a two-minute timeout, and growing conversation history eventually requires a new task. **Pause** cancels the current request or command process group. **Cancel task** ends the task; **Delete** removes its board, journal and agent conversation. Closing the interface does not pause background work. Tasks retain up to 300 board entries and 200 journal events; there can be up to 200 tasks per administrator.

A server restart pauses interrupted jobs; continuation is manual. An action interrupted while executing has an unknown outcome and is never automatically retried. Verify the external result before asking for any replacement action. Task ownership is checked on every request, including action reviews.

The isolated tests `test_agents.py` and `test_agent_provider.py` exercise permission gates, private conversation isolation, the existing provider pipeline, immutable reviews, cancellation, restart recovery, state validation and execution limits without a paid model or personal chat data. `test_agents_browser.cjs` checks desktop and phone layouts, task creation, site editing, reviews, preserving a normal chat's draft and hiding or locking unavailable features. It accepts the same external Playwright configuration as the other browser checks.


## General project workspaces (initial implementation)

Agent mode opens a separate list of project workspaces. These are not the ordinary mvmAI code-directory projects. Create a workspace by describing the project and what you want to achieve; an optional advanced selector links an existing code project for its working directory. The existing provider settings supply the AI. Each workspace has one visible conversation, with Live, Overview, Tasks, Tools, Knowledge, Resources and Activity views. The initial Activity page shows an interactive execution map with the agent, selected model, plan, searches, reads, commands, project tools, memory, your decisions and results. These are operation types, not invented additional agents. A request travels from the agent to the active operation; a newly received result briefly travels back. Existing history is not replayed when opening or returning to the page, switching projects, restoring the app or returning from a background tab. A return pulse is removed when its animation ends or when the Activity page is left. New results are animated only while the map is continuously visible; completed or paused work has no running flow. Commands queued for review remain distinct from executed commands.

Select any node for an explanatory popup with its recorded actions and outcomes. Select a real task step below the map to inspect its action, result and next requirement. An outstanding question or approval pulses on Your decision and the relevant command, tool or step; the popup offers the same reply or exact-action review controls. Waiting steps remain visible even while independent work continues. An explicit reply opens the conversation on phones. The Activity map fills the available app content box and adjusts its rings, labels and wire endpoints when the app window is resized. Repeated status headings and separate result/question/activity blocks no longer push the diagram below the viewport: use its nodes for those details and History for the journal. Task steps occupy a bounded horizontal strip rather than expanding the map vertically. Short windows use compact labels or icons, retaining full accessible names and clickable explanations. On phones the conversation starts as a compact Expand chat bar; Collapse chat collapses it again; the same compact header, navigation, panel split and conversation state are shared across every page, so switching tabs does not move the screen. Outstanding questions show their actual next action in the persistent status bar. Its pulsing action button opens the question or approval directly from any page; the relevant Activity, Tasks or Tools menu is highlighted, as are reply controls and pending review cards. Indicators clear when the requirement is resolved. Animation respects reduced-motion preferences. The conversation has more space on desktop and sits below the work panel on phones. Enter sends a message; Shift+Enter inserts a new line. Replies support bold text, inline and fenced code, and HTTP(S) Markdown links; source HTML is always escaped. Switching back to ordinary chats preserves the mounted chat and its draft.

The agent receives general tools for maintaining a concise overview, knowledge notes with sources, resource descriptions, tasks and graphical views. It can discover bounded directory candidates on the server, inspect selected directory metadata and read bounded text files inside a selected resource. This is read-only administrator discovery, independent of the server execution toggle; there are no hardcoded store, framework or SEO workflows. Common credential files are excluded and obvious credential-bearing lines are omitted from text reads. This is not a credential vault and should not be used to store passwords, tokens or API keys.

Graphical views are declarative forms, tables and notes rendered by the application, not model-authored HTML or JavaScript. Forms support text, longer text, numbers with bounds, single/multiple selections and booleans. Labels and options come from the actual project. The server validates allowed values and the exact view revision before accepting a choice. The selection returns to the same project conversation. Table output is escaped and bounded. Forms can also open a saved tool. Obsolete views can be removed, and the agent can remove obsolete knowledge/resources or archive tools through its structured tools.

Each user request becomes or resumes an internal execution. Completed requests are followed by fresh internal sessions automatically; neither internal session IDs nor chat selection controls appear in the workspace UI. A message arriving during work is queued for the next round or following execution. Pending approvals hold the queue until they are resolved. The visible conversation is stored independently from execution transcripts and supports loading earlier messages. Project knowledge, a bounded index and recent conversation supply context to new work. When an execution transcript grows beyond roughly 90 KB, the runtime creates a new private session with a deterministic checkpoint of its goal, user instructions, board and recent results. Detailed previous execution transcripts remain in the private database. Checkpoints are bounded and are not a lossless replacement for all prior context: the agent must keep important findings and decisions in project knowledge. This reduces repeated context loading but does not guarantee lower cost for every task.

### Model and live status

The new-project form also asks for the provider and model; it starts with the configured default, and the choice is kept for the project. The header of a workspace shows the provider and model new work uses: the project's own choice, or the configured default when none was chosen. Select it to change the provider and model. The choice applies to the whole project. A task that is not finished continues in a new internal session on the new model and keeps its instructions, board and recent results; the conversation shows a note that it continued on another model. The change is refused while the agent is working or while a command waits for review, so finish or pause the work first. Only administrators with the feature can change it.

A status line under the header shows what the agent is doing now: asking the model (with the round number), searching the web, reading a page, updating the plan, preparing or running a command, or using a project tool, with a running timer. It also shows when the agent waits for approval or for a reply, is paused, has stopped with a problem or is idle. The status is live information, not a journal entry.

### New work from the agent

Polling preserves the selected tab, the chat draft and input focus. Status, task progress and new conversation messages continue to update while you compose. New messages follow the bottom only when you are already there; reading older messages does not force the conversation to the end. Recent activity is collapsed by default; the separate History tab retains the journal. The completed state shows the most recent finished request.

### Deleting a project

The **Delete project** action in the header’s additional-actions menu, after an in-app confirmation, removes the project together with everything it stores: its tasks and their history, the conversation, the agent's private model sessions, notes, resources, saved tools and views, and the files you attached. A file that another project or chat still uses is kept until its last user is deleted. A project cannot be deleted while a task is running or waits for approval; pause or finish it first. Nothing is removed automatically with time.

Files, folders or applications the agent created elsewhere on the server (for example a site or app you asked it to build) are never deleted with the project, because they belong to you, not to the project.

### Approval levels

A selector in the project header, next to the model, sets how much the agent may do in this project without asking. The choice is saved for the project and applies to the agent's commands and to saved tools.
• Ask every time (default): every command and every tool run waits for your approval.
• Auto: read-only: a tool preview and a single plain read command (ls, cat, head, tail, grep, wc, pwd, stat, file, du, df, date, whoami, or find without write options) run on their own. Anything with shell syntax such as pipes, redirection, substitution or wildcards, any command that writes or deletes, and every tool execution still wait for you.
• Fully automatic: everything the agent queues is approved and continued at once, as in the automatic chat mode. The agent then works alone and asks you only when it needs a decision, such as a choice between options or missing information, never to confirm a command.

Automatic approval records the same exact action and execution scope as a manual one, and the activity log marks it with [auto]. Raising the level also releases what is already waiting. Server execution must still be enabled in the settings, and the limit of two running tasks applies. Activating a new tool version remains your decision at every level.

When an action waits for approval, its review card is available in every workspace tab. The status line provides a Review shortcut. A request for a human decision shows the exact question and recommendation in the conversation and in a Live card with a Reply in chat button. The agent is instructed to ask before major decisions outside your authorization, such as spending money, deleting valuable data, publishing or changing access. This decision policy guides the model; automatic command approval itself does not classify command consequences.

A plain progress reply no longer puts the project into a waiting-for-user state. The runtime prompts the model to continue with tools, finish verified work or explicitly request a decision with `agent_wait`. After three consecutive replies without any tool call it pauses with a clear model-action diagnosis instead of looping indefinitely or pretending to need your answer. Continue retries the work; a different model can also be selected while paused.

### Attachments

The project conversation has a paperclip button next to the message box. Choose files, drop them on the box or paste a screenshot from the clipboard. Each file is uploaded to the administrator's own upload folder on the server, the same as in the ordinary chat, and an archive is unpacked there. The message carries the file path, and the conversation shows only the file name. A CLI model (Claude, Codex, Gemini) can open the file by that path. An API model cannot see a picture or open a file by itself; it can only ask for a reviewed command, so use a CLI model when it must look at screenshots.

### Short sessions

An agent session is short-lived on purpose. The project keeps what matters (knowledge, resources, overview, views, tools), and the agent is told to save every finding, decision and next step there before it waits or finishes. A new session needs only the project index, the recent visible conversation and a short checkpoint.

When an unfinished task is continued by a message, by Continue or by choosing a board item, it keeps its session only if it answered recently and is still small. If more time has passed than the chat restart time (60 minutes by default, the same History setting as the chat) or the session holds more than 40,000 characters, the task continues in a new session with a checkpoint of its instructions, board and the last eight messages, each shortened. The visible project conversation stays one. A task that is still working is never renewed from outside, and neither is one with a command waiting for review. The Tasks tab shows each session's current size.

## Generated reusable tools

The agent is told to prefer helpers over repeating mechanical, repeated or data-heavy work in the conversation, which saves model requests. The project index given to every new session lists each active or draft helper with a short description and its input names, so a fresh session can pick a ready helper with `workspace_request_tool` without reading its code. If nothing fits and the work is likely to return, the agent writes a small helper (a draft awaiting your activation) and updates an existing one by id instead of making copies. Archived helpers are left out of the index.

The agent can save a reusable Python tool with a description, a validated input form and declared dependencies on other saved tools. Each revision is immutable and has a digest covering its source, form, description, declared dependencies and resource-description revision. New revisions remain drafts until an administrator explicitly activates the exact version. Syntax checking parses the code but does not test its behavior. Source is available in the version details. An administrator can reactivate a previous version while its resource revision remains applicable, or archive a tool without deleting its versions.

The tool program reads one JSON object from stdin: `phase` (`preview` or `execute`), `params`, `project` (workspace id and resources), and `preview` (the prior successful preview output for an execution). It prints JSON with a human-readable `summary` and optional string `columns` and object `rows`, or plain text. Preview code is instructed to avoid writes. A mutating tool must re-read the external data and reject changes since its preview; the generic runner cannot enforce an arbitrary external system's transaction semantics.

The same saved form and execution path serve both human invocations and the agent's `workspace_request_tool`. Each invocation is queued with an immutable version/source digest, validated parameters, phase and Linux execution scope. Review it before approving. The UI starts an approved invocation when no other approvals remain. Even previews require an invocation approval. Execution additionally requires an earlier successful preview for the identical version and parameters. Changing the active version, archiving it or changing the workspace resource descriptions prevents a stale queued invocation from running. These checks do not automatically detect every change in external files or remote services.

Saved-tool invocations execute without an AI request in a separate Python subprocess, never by importing generated code into the application server or interpolating field values into shell text. Existing administrator server-execution permission is still required. Activated Python has that account's host privileges; this is not an operating-system sandbox, and a preview phase is a program contract rather than a security boundary. Input/output are bounded and invocations time out after two minutes. Pause cancels the process group. A restart or cancellation with an uncertain outcome does not automatically replay the action. The interface retains the result and returns it to the project's conversation.

The stable mvmAI implementation provides storage, rendering, ownership, approvals and execution. Generated project code remains in versioned extension records rather than rewriting mvmAI's own implementation. All workspace endpoints remain behind the existing Premium module, enabled setting and administrator checks. An encrypted account vault, general browser-session manager, scheduled monitoring and a complete autonomous software-maintenance policy remain future extensions.

Execution traces retain the latest 80 bounded public operation records per task, with start, completion, error or waiting state and a board-item reference where known. They exclude private model reasoning and full tool payloads. Older tasks without traces use only available journal facts and current activity; missing records appear as no activity.

Workspace regression checks are in `test_workspaces.py`. `test_activity_graph_model.cjs` checks factual graph states, and `test_activity_graph.cjs` verifies directed requests/results, no repeated history animation, inspectable nodes and steps, waiting decisions, focus, mobile chat sizing, both host themes and reduced motion. `test_workspaces_browser.cjs` runs a disposable local backend with deterministic model replies and verifies real workspace forms, persisted knowledge, version activation, reviewed previews and executions, keeping the ordinary chat draft, and running saved operations without further AI requests at desktop and phone widths. No live project, personal chat or external publication is modified. The fixture is `workspace_server.py`; Playwright can be supplied with `MVMAI_PLAYWRIGHT_MODULE`. `test_agents_settings.cjs` verifies Premium settings and free-install locking.

## Pictures

mvmAI can make pictures, in its own chat and for other apps. Which generator makes them is a setting in mvmAI (Pictures, under the provider settings): Automatic takes the first that is ready, in this order — Codex's built-in image tool (run as the Linux account Codex is signed in with, so a picture costs no more than the subscription already does), then the OpenAI images API, then Google's Gemini image model, the last two with the key mvmAI already holds. The list in the settings shows which are ready; a generator can also be chosen by name, or pictures switched off. A new generator is one more entry in `backend/apps/mvmai/images.py`.

In the chat the assistant gets a "make a picture" tool whenever a generator is ready, for everyone except an administrator with full access on Codex, and for the others only when the administrator allows it (Let public users make pictures, off by default); with full access (command execution on and automatic) Codex keeps its own picture tool, so an administrator makes pictures as before; an administrator on Claude or Gemini CLI, or without full access, gets the tool like anyone else. The administrator can set a daily limit per public user, and a price in credits per picture under Apps Hub (Credit services, "AI picture"), charged first and given back when no picture is made. The picture appears in the chat with a download link and is kept with the chat; a person's pictures are deleted after 90 days. A picture takes a minute or more.


## Services for other apps

Through the app API mvmAI answers two things for other apps: `ask` (a one-off question to the public-page AI; the prompt may be up to 200,000 characters when the asker requests it, 20,000 by default) and pictures.

`image_status` says whether a picture can be made, and `image` makes one for a profile (`aspect` is portrait, landscape or square). An asking app never learns which generator answered; the choice is the one made in the Pictures settings (stored as `image_backend`: `auto`, `codex-cli`, `openai`, `gemini` or `off`; `image_model_openai` and `image_model_gemini` change the model). Like `ask`, both functions work only after the administrator switches mvmAI's app API on, and they are marked internal so the assistant never offers them as tools. Pictures are not stored and no chat credits are charged: the asking app decides what a picture costs.
